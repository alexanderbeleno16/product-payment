# Hito 3 verification — local evidence, 2026-09-27

This matrix compares the private technical brief, the [repository diagrams](../README.md), and the implemented SPA/API. It records observed local evidence, not a certification of live payments or deployment.

| Brief / architecture requirement | Implemented boundary | Verification and remaining gap |
| --- | --- | --- |
| Five-step, single-product mobile flow | Catalog and product, card/delivery modal, summary with confirmation dialog, status screen, return to server-refreshed product (`frontend/src/App.tsx`, `frontend/src/features/checkout/`). | DOM Jest and Playwright/Brave with a mocked local API exercised 320×568, 375×667, 542×932, and 1280×800 CSS-pixel viewports: Tab/Escape and focus behavior, one checkout POST, then refresh with status GET only. Catalog is optional, not a cart. At 200% root-font proxy, the summary/dialog remained usable but pre-existing product/gallery content overflowed a 320px viewport to 394px. Native browser zoom, a physical phone, and a second browser engine were not verified. |
| Server-owned product, fee, delivery, and total | `GET /checkout/quote`; summary displays line items, while `POST /checkouts` requires `expectedTotalCents` checked against a new server quote before payment (`frontend/src/features/checkout/SummaryScreen.tsx`, `backend/src/application/start-checkout.ts`). | Fake and PostgreSQL HTTP tests cover a changed total with no transaction, stock, delivery, or outbound payment effects. The client amount is a precondition, never authority. |
| Explicit, idempotent payment initiation | Confirmation event calls `submitPayment`; a UUIDv4 key is saved synchronously before one POST (`frontend/src/app/paymentFlow.ts`, `frontend/src/app/paymentRecovery.ts`). Backend uses a unique key and durable submission claim. | DOM and backend tests cover double-click, same-key replay, concurrent requests, ambiguous response, and no blind re-POST. The initial response is not displayed as final approval. |
| Real payment and fulfillment states | Signed event triggers authoritative server lookup and guarded finalization; browser reads only local `GET /checkouts/status` by original key (`frontend/src/features/checkout/PaymentStatusScreen.tsx`, `backend/src/application/get-transaction-status.ts`). | Fake and PostgreSQL tests prove pending/failure leave stock and delivery unchanged, approval creates one delivery, and approved-without-stock remains a distinct exception. Live terminal approval and deployed callback are unverified. |
| Recovery after refresh/lost response | Versioned storage allowlist retains product ID, quantity, and key, never card/token/contact/consent values. Bounded status checks and manual recheck preserve uncertainty (`frontend/src/app/paymentRecovery.ts`, `frontend/src/app/paymentFlow.ts`). | DOM Jest covers refresh, rejected 404, ambiguous 404, unreadable storage, and stock exception. Storage failure blocks a fresh payment instead of risking duplication. |
| Browser-side card tokenization | `frontend/src/api/cardTokenization.ts` obtains a public encryption key and sends compact RSA-OAEP-256/A256GCM JWE through the same-origin API; the server returns an opaque token only. | Existing boundary tests mock JOSE and network. `cardTokenization.crypto.test.ts` uses real JOSE with an in-memory RSA key and decrypts the emitted JWE; no provider call or persistent secret. Prior sandbox smoke test reached tokenization and pending initiation only. Browser/provider interoperability, PCI scope, and live final payment are **not** established by these tests. |
| Maintainable React/Flux boundaries | Redux owns cross-screen non-sensitive state; the confirmation handler owns the POST; Effects synchronize GET/polling with cleanup. Runtime JSON and storage are narrowed at adapters. | Reviewed against local React, Redux, clean-code, accessibility, and provider skills plus the [primary-source map](../.agents/skills/_shared/sources.md). This is review evidence, not a claim that every component or runtime path is flawless. |
| Jest in both apps with >80% coverage | Frontend Jest+SWC/Testing Library and backend Jest+PostgreSQL test suites; CI enforces `80.01` on all four coverage metrics in each app. | Frontend: 15 suites/112 tests, statements 92.92%, branches 90.13%, functions 95.53%, lines 94.85%. Backend with disposable PostgreSQL: 27 suites/147 tests, 90.17%/86.03%/85.90%/90.87%; E2E 6 suites/37 tests. Build/lint passed in both apps. |

The local provider skill is intentionally Git-ignored; its snapshot is guidance, not proof of current remote behavior. The current provider protocol was reviewed separately against primary documentation, but no new live payment request was made for this work unit. A public AWS endpoint, edge/distributed tokenization abuse controls, production status authorization, and end-to-end terminal-payment verification remain before public delivery. The last architecture diagram in the root README is a proposal, not deployed infrastructure.
