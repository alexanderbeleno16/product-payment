# Frontend del checkout

React, TypeScript, Vite y Redux Toolkit impulsan la SPA de checkout diseñada primero para móviles. **Alcance local actual (del catálogo al estado del pago):** el catálogo de ShopiFast, en español de Colombia, consulta la lista de productos mediante `GET /products`, ofrece una ruta de regreso desde el producto seleccionado y permite elegir una cantidad disponible para obtener una cotización calculada por el servidor. Se muestran estados de carga, catálogo vacío, error, reintento y producto agotado. Una actualización del catálogo en segundo plano mantiene visibles las tarjetas ya cargadas y advierte cuando sus datos podrían estar desactualizados tras un fallo; seleccionar un producto siempre consulta su detalle vigente por ID. La API conserva la autoridad sobre nombres, descripciones, precios, existencias, cotizaciones y estado final del pago y la entrega.

El catálogo presenta diez productos de demostración cargados inicialmente en una cuadrícula adaptable, pero el checkout sigue procesando **un solo producto seleccionado por vez**; no hay carrito ni pago de varios artículos. La selección restablece el producto, la cantidad, la cotización y las identidades de solicitudes pendientes anteriores antes de consultar el nuevo producto por ID. Las fotos de producto y la marca de la tienda son recursos locales optimizados bajo `public/`. Las imágenes no se almacenan en PostgreSQL ni se sirven desde la API de productos; un producto desconocido muestra un estado neutro de imagen no disponible, en lugar de una foto incorrecta. Cada producto inicial tiene dos vistas WebP locales en un manifiesto por ID de producto; la galería de detalle admite flechas, miniaturas y un modal que ocupa toda la pantalla, con navegación por teclado, Escape y restauración del foco. En el catálogo, las dos primeras imágenes de la lista visible se cargan de inmediato (la primera con alta prioridad de descarga) y las posteriores se cargan de forma diferida con dimensiones intrínsecas reservadas. En el producto seleccionado, ambas imágenes se cargan de inmediato mediante las miniaturas para que la vista ampliada reutilice las mismas URL. Esto optimiza la carga inicial probable y la reutilización de imágenes, pero no constituye una medición de latencia de producción. El logotipo textual ShopiFast usa una fuente Grand Hotel alojada localmente desde `@fontsource/grand-hotel` (OFL-1.1), aplicada solo al texto de marca; no requiere una CDN de fuentes.

La acción del producto abre el modal accesible **Tarjeta y entrega**. Valida los datos de tarjetas Visa/Mastercard, contacto y entrega; presenta dos documentos de consentimiento vigentes obtenidos mediante `GET /checkout/consents` como opciones independientes sin marcar; y tokeniza la tarjeta en el navegador solo después de un envío explícito y válido. La vista previa animada de la tarjeta muestra como máximo los primeros ocho dígitos y un código de seguridad enmascarado. El navegador cifra los datos de la tarjeta localmente y envía solo un JWE compacto al `POST /checkout/card-tokens` del mismo origen; la API lo retransmite a un destino fijo de prueba y devuelve únicamente un token opaco. Los datos sin cifrar de la tarjeta nunca ingresan a la API. El resumen vuelve a solicitar la cotización al servidor y muestra el producto, las tarifas obligatorias de base y entrega, el total, los datos de entrega y los datos enmascarados de la tarjeta. La acción de pago abre un diálogo nativo de confirmación con el importe final; solo su manejador de confirmación explícita llama a `POST /checkouts` con `expectedTotalCents` y la clave UUIDv4 original de `Idempotency-Key`. El backend rechaza un total modificado antes del pago. La pantalla de estado consulta el estado local del pago y de la entrega, ofrece consultas automáticas acotadas y consultas manuales, y vuelve al producto recién consultado cuando el resultado se resuelve de forma segura. Se observaron aprobación terminal y finalización locales en el entorno de prueba tras una conciliación del operador; el frontend desplegado y la recepción pública de eventos siguen sin verificarse.

Antes del pago, se guardan en el `sessionStorage` de esta pestaña el ID y la cantidad del producto, con versión, junto con un borrador de contacto y entrega restringido a campos permitidos. El borrador contiene únicamente correo electrónico, destinatario, dirección y ciudad; se elimina cuando el checkout se completa o se abandona. No persiste entre pestañas ni entre sesiones del navegador. Al actualizar la página se vuelven a consultar el producto y la cotización, y deben introducirse otra vez los datos de la tarjeta y ambos consentimientos. Inmediatamente antes del POST, una lista permitida independiente y versionada guarda el ID del producto, la cantidad y la clave de idempotencia aleatoria original. Una actualización de página o la pérdida de la respuesta del POST se recupera mediante el `GET /checkouts/status` de solo lectura con esa clave; no crea un pago nuevo. Si existe un registro de recuperación ilegible, se bloquea un nuevo envío para evitar un segundo cobro. Un POST rechazado sigue asociado a su clave hasta que una consulta de estado confirme que no hay transacción local. El número de tarjeta, nombre del titular, vencimiento, código de seguridad, token y tokens de consentimiento no se guardan en Redux ni en el almacenamiento del navegador. Permanecen transitorios en la instancia actual de la aplicación y se descartan después de iniciar el pago o navegar. `APPROVED` con `STOCK_UNAVAILABLE` no equivale a una entrega: la pantalla conserva el seguimiento y la opción de volver a consultar, y no ofrece repetir la compra.

## Ejecutar localmente

Vite 8 requiere Node.js `^20.19.0 || >=22.12.0`. Este frontend se verificó con Node.js `v24.20.0` y npm `11.19.0`; el proyecto no declara un rango independiente para el motor de npm.

1. Inicie el [backend](../backend/README.md#ejecutar-localmente) en `http://localhost:3000`. Su configuración local requiere PostgreSQL, datos iniciales y configuración del servidor no versionada incluso para consultar productos.
2. Desde `frontend/`, ejecute:

   ```bash
   npm ci
   npm run dev
   ```

3. Abra la URL local que muestra Vite (normalmente `http://localhost:5173`). El proxy de desarrollo reenvía las solicitudes de productos y checkout a `http://localhost:3000`. También reenvía el puente de tokenización del mismo origen. Configure el servidor de prueba y la clave pública correspondiente únicamente en el backend; Vite no requiere URL ni clave del proveedor. El navegador no llama directamente al entorno de prueba porque la respuesta observada del GET de clave UAT carece de la cabecera CORS para navegador. La interoperabilidad de la tokenización JWE con un navegador y el proveedor reales sigue sin verificarse.

Para producción, dirija `/checkout/*` y `/checkouts/*` desde el origen de la SPA hacia la API Nest mediante HTTPS y con la caché desactivada; conserve las llamadas actuales de tokenización en el mismo origen. Las consultas de productos pueden seguir usando la variable pública `VITE_API_BASE_URL`. Un origen de API separado requiere configurar deliberadamente CORS y la política de seguridad del navegador. No ponga secretos del servidor en Vite. Un `503` de `/checkout/consents` impide continuar y muestra una acción de reintento; configure el backend en lugar de omitir los consentimientos. La protección actual contra abuso de la tokenización es local a cada proceso; un despliegue público con varias réplicas necesita controles distribuidos o perimetrales y una identidad de proxy verificada. No ponga secretos del servidor en variables `VITE_*`.

## Verificar

Ejecute desde `frontend/`:

```bash
npm run build
npm run lint
npm test -- --runInBand
npm run test:coverage
```

Observado localmente el 2026-09-27 para el frontend del checkout del Hito 3: compilación y lint correctos; Jest pasó **15 suites / 112 pruebas**. La cobertura fue de **92.92% de sentencias, 90.13% de ramas, 95.53% de funciones y 94.85% de líneas** en el alcance configurado de `src/`. `frontend/jest.config.cjs` exige superar estrictamente el 80% en las cuatro métricas. Las pruebas cubren el comportamiento visible de confirmación y estado, la recuperación segura sin duplicar el POST tras actualizar la página, cambios en la cotización, obligatoriedad de los consentimientos, errores y reintentos, y un contrato real de cifrado y descifrado JOSE JWE compacto con una clave RSA desechable en memoria y una red del mismo origen simulada. Esto último constituye evidencia criptográfica local, **no** interoperabilidad real entre navegador y proveedor. La configuración del origen de API exclusiva de Vite se simula en Jest y no tiene cobertura directa de Jest. Estas cifras no prueban la recepción de eventos ni un despliegue públicos; la aprobación local observada por separado en el entorno de prueba requirió conciliación del operador.

La pantalla anterior de producto único se inspeccionó visualmente en el navegador integrado a ancho de escritorio y en Brave a `375 × 667` y `320 × 568` píxeles CSS. Esas comprobaciones usaron una API local desechable simulada, no el backend real. Las pruebas de navegador de confirmación y estado a 320, 375, 542 y 1280 píxeles CSS con una API simulada cubrieron el foco de teclado y la recuperación tras actualizar la página; el zoom nativo, un teléfono físico y un segundo motor de navegador siguen sin verificarse. Por separado, transacciones locales de prueba alcanzaron la aprobación terminal mediante conciliación del operador, incluido un recorrido de compra en navegador. Esto no verifica la entrega pública de eventos ni la recuperación automática en AWS.
